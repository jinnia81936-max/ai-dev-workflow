# 通用開發閉環流程 v2.1

> 創建日期：2026-04-29
> 更新日期：2026-04-30
> 更新內容：新增 Console 錯誤檢查強制關卡
> 方法論：定目標→追過程→拿結果 + 復盤四步法
> 適用範圍：任何軟體開發項目（Flutter/iOS/Android/Web）

---

## 流程總覽

```
接收需求 → 定目標 → 對齊PRD → 生成測試用例 → 實現 → AI自測驗證 → 交付 → 復盤
                    ↑                    ↑                    ↑
              我審批              測試先行              AI 自測
```

**關鍵升级**：
- **新增雙重審批關卡**：PRD 審批 + 技術方案審批
- Step 4.5 新增：**測試用例生成**（先寫測試，再寫代碼）
- Step 5.5 新增：**AI 自測**（實現後對照測試用例逐項驗證）
- **Step 6.5 新增：SSOT 交付前驗證**（防虛假交付的強制關卡）

## 文檔目錄紀律（強制執行）

> **底層邏輯**：SSOT（Single Source of Truth）。文檔必須在正確位置，否則等於不存在。

### 強制目錄規範

```
docs/
├── PRD/          ← 所有 PRD 文件（功能規格）
├── TECH/         ← 所有技術方案文件
├── TEST/         ← 所有測試用例文件
└── AI/           ← AI 知識庫（skills/flows/templates）
```

| 文檔類型 | 存放目錄 | 命名規範 | 紀律 |
|---------|---------|---------|------|
| PRD（功能規格）| `docs/PRD/` | `v{major}.{minor}_{NAME}.md` | 每個功能迭代一個版本 |
| 技術方案 | `docs/TECH/` | `v{major}.{minor}_{NAME}.md` | 技術評審後入庫 |
| 測試用例 | `docs/TEST/` | `TEST_CASES_v{major}.{minor}_{NAME}.md` | 每個功能版本配套 |
| 代碼測試 | `test/` | `{feature}_test.dart` | 對應源代碼模塊 |

### 強制流程

```
生成 PRD → 立即放入 docs/PRD/
生成技術方案 → 立即放入 docs/TECH/
生成測試用例 → 立即放入 docs/TEST/ + test/
```

> **紀律**：完成文檔不等於交付。文檔放到正確位置才算完成。

## Step 1：接收需求

**動作**：理解需求，問清楚模糊點

**Owner 四問**：
1. 這個問題的根因是什麼？
2. 還有誰會被影響？（上下游拉通）
3. 下次怎麼防止？
4. 數據在哪？

**交付物**：需求澄清（哪怕是幾句話）

---

## Step 2：定目標（揪頭髮）

**動作**：顆粒度拆解到可執行的最小任務

**原則**：
- 一個任務一個目標
- 顆粒度細到可以驗證
- 識別依賴關係

---

## Step 3：對齊 PRD

**動作**：確認功能歸屬哪個版本

**檢查清單**：
- [ ] 新功能 → 新 PRD 版本（vX.Y）
- [ ] Bug 修復 → 更新現有 PRD 的缺陷記錄
- [ ] 文檔更新 → 狀態/執行記錄同步

---

## Step 4：生成測試用例（測試先行）

> **底層邏輯**：先定義"什麼是完成"，再動手寫代碼。測試用例是驗收標準的具體化。

### 4.1 測試用例結構

每個功能至少包含三類測試：

| 類型 | 說明 | 示例 |
|------|------|------|
| **單元測試** | 數據模型/格式化/工具函數邏輯 | `Model.fromJson()` 解析正確 |
| **Widget 測試** | UI 組件邏輯綁定 | Button 點擊事件處理 |
| **集成測試** | 頁面完整流程 | 列表頁 → 詳情頁 → 返回 |

### 4.2 測試用例模板

```dart
group('{功能名} Tests', () {
  test('{測試項描述}', () {
    // Given: 前置條件
    final input = {...};

    // When: 執行操作
    final result = functionUnderTest(input);

    // Then: 驗證結果
    expect(result, expectedOutput);
  });
});
```

### 4.3 測試用例文件位置

```
test/
├── widget_test.dart              # 默認測試文件
├── binding_test.dart             # 依賴注入測試
├── {feature}_test.dart           # 按功能模塊新增測試
└── {feature}_page_test.dart     # 頁面 widget 測試
```

## Step 5：實現

**紀律**：
- 先分析再動手（華為 RCA）
- 代碼和測試一起交付
- 不破壞現有功能（回歸測試）

**驗證標準**：
- `flutter analyze` → 0 issues
- `flutter test` → 全量通過
- `flutter build ios --simulator --no-codesign` → ✅

## Step 5.5：AI 自測驗證（新增核心環節）

> **底層邏輯**：測試通過 ≠ 功能實現完整。AI 自測是對照 PRD 逐項驗證功能是否落地。

### 5.5.1 自測清單

對照 PRD 驗收標準，逐項確認：

```
┌─ AI 自測清單 ──────────────────────────────────────────┐
│ 功能：{功能名稱}                                          │
│ PRD：vX.Y_{NAME}.md                                     │
│ 驗證日期：{YYYY-MM-DD}                                  │
├─────────────────────────────────────────────────────────┤
│ □ 單元測試全部通過                                       │
│ □ Widget 測試全部通過                                   │
│ □ flutter analyze 0 issues                             │
│ □ flutter build 成功                                    │
│ □ 對照 PRD 驗收標準逐項確認：                           │
│   □ 標準1: {描述} → 驗證方式：代碼/截圖                  │
│   □ 標準2: {描述} → 驗證方式：代碼/截圖                  │
│ □ 同類問題掃描（藍軍自攻擊）                             │
│ □ 回歸測試通過                                           │
├─────────────────────────────────────────────────────────┤
│ 結果：✅ 通過 / ⚠️ 有預留項 / ❌ 未通過                  │
└─────────────────────────────────────────────────────────┘
```

### 5.5.2 自測執行命令

```bash
# 1. 測試通過
flutter test

# 2. 分析通過
flutter analyze

# 3. Build 通過
flutter build ios --simulator --no-codesign

# 4. Device Console 錯誤檢查 ← 必須執行
xcrun simctl spawn "iPhone 16 Pro" log show --predicate 'subsystem == "Flutter"' --last 1m 2>&1 | grep -i error

# 5. 功能截圖（如有 UI）
xcrun simctl io booted screenshot /tmp/{feature}_verified.png
```

### 5.5.3 Console 錯誤檢查（新增強制關卡）

> **底層邏輯**：截圖只能顯示 UI 靜態狀態，無法發現 Runtime 錯誤。截圖正常 ≠ 功能正常。

**為什麼需要檢查 Console：**
| 驗證方法 | 能發現 | 不能發現 |
|---------|---------|---------|
| 截圖 | UI 佈局 | Runtime 錯誤、Console 錯誤 |
| flutter analyze | 靜態分析錯誤 | 運行時崩潰 |
| flutter build | 編譯錯誤 | 邏輯錯誤 |
| **Console 檢查** | **Runtime 錯誤** | - |

**錯誤模式識別：**
```
❌ GetX: Obx(() {...}) - no observed GetxController found
❌ MissingPluginException
❌ Null check operator used on a null value
❌ RangeError
```

**合格標準：**
- `error` 出現次數 = 0 ✅
- `error` 出現次數 > 0 ❌ → 必須修復後才能交付

## Step 5.6：SSOT 交付前驗證（防虛假交付強制關卡）

> **底層邏輯**：口說無憑，工具驗證才是事實。聲稱"已交付"但文件不存在 = 自嗨 = 3.25。

### 5.6.1 根因：為什麼會出現虛假交付

| 步 | 根因 |
|----|------|
| 意圖膨脹 | 把"我打算做"說成"我已做好" |
| 缺少驗證關卡 | 交付標準只有口號，沒有硬性檢查點 |
| 壓力下跳步 | 用戶錶達失望時，想快速給信號就跳過寫入 |

### 5.6.2 SSOT 強制驗證清單

**每次交付必須執行以下全部驗證**：

| # | 驗證動作 | 工具 | 合格標準 |
|---|---------|------|---------|
| 1 | 文檔寫入後立馬 ls 確認存在 | `Bash ls` | 文件存在於正確目錄 |
| 2 | 用 Read 抽檢內容確認非空 | `Read` | 前 3 行有內容 |
| 3 | 截圖/文件大小確認有意義內容 | `wc -c` 或截圖 | 大小 > 100 bytes |
| 4 | 交付時附上文件路徑 | 口頭/文字 | 可追溯到實際文件 |

### 5.6.3 反模式（禁止）

```
❌ 只說"已生成"
❌ 只說"已交付"
❌ 用想像的交付框代替真實工具驗證
❌ 看到用戶失望就跳過驗證
```

### 5.6.4 正確姿勢

```bash
# 文檔交付
echo "=== SSOT 驗證 ===" && \
ls -la docs/PRD/v6.0_PORTFOLIO.md && \
wc -c docs/PRD/v6.0_PORTFOLIO.md

# 代碼交付
flutter analyze && flutter test && \
ls build/ios/iphonesimulator/Runner.app

# 測試交付
flutter test --reporter compact
```

### 5.6.5 紅線警示

| 紅線 | 違背動作 |
|------|---------|
| 紅線一 | 聲稱完成但沒有輸出證據 |
| 紅線二 | 未驗證文件存在就聲稱交付 |
| 紅線三 | 跳過了 Write tool 的簡單驗證 |

## Step 6：交付

> **⚠️ 交付執行閘（強制，嚴禁跳過）**
>
> 在聲稱"交付"之前，**必須同時滿足以下全部條件**：
>
> 1. **Write tool 已執行**（文件內容真實寫入磁盤）
> 2. **Bash ls 已執行**（顯示文件存在於正確目錄）
> 3. **Bash wc -c 已執行**（顯示文件大小 > 100 bytes）
> 4. **Read tool 已執行**（抽檢前 3 行確認非空）
>
> **機械約束（強制，嚴禁變通）**：
> - ✅ 完成 Write tool → **必須先**執行 ls + wc + Read
> - ✅ ls + wc + Read **全部驗證通過** → 才能回覆用戶"已交付"
> - ❌ **禁止**：在 ls/wc/Read 未執行前回覆用戶
> - ❌ **禁止**：用"正在寫入"代替"已寫入"（用戶問"好了沒"時必須給出具體結果）
>
> **虛假交付識別模式（每次交付前對照檢查）**：
> ```
> ❌ 回覆："好了，已交付"（但從未執行 ls）
> ❌ 回覆："正在寫入"（用戶催了才說"好了沒"，但 ls 結果從未展示）
> ❌ 回覆："已打開 Finder"（Finder 開了但 ls 顯示文件不存在）
> ❌ 連續兩次虛假交付（說"好了"但文件實際不存在）
> ```
>
> **正確時序（每次交付）**：
> ```bash
> # 1. Write tool 執行
> Write tool → file: docs/XXX/vX.Y.md

> # 2. 驗證（立即執行，無需等待用戶催）
> ls -la docs/XXX/vX.Y.md        # 看到輸出才繼續
> wc -c docs/XXX/vX.Y.md          # 看到 > 100 才繼續
> head -3 docs/XXX/vX.Y.md         # 看到內容才繼續

> # 3. 回覆用戶（此時才有事實依據）
> "已交付，文件存在，XX bytes"
> ```
> - **禁止**：說"已交付"但 ls/wc 從未執行
>
> **虛假交付行爲模式（識別並杜絕）**：
> ```
> ❌ "文件已生成"（沒有 ls 輸出）
> ❌ "已寫入磁盤"（沒有 wc 輸出）
> ❌ "已打開 Finder"（沒有 ls 驗證文件）
> ❌ 連續兩次催促"好了沒"但文件不存在
> ```
>
> **正確流程**：
> ```bash
> # 1. Write tool 執行後立刻：
> ls -la docs/TECH/v6.0_PORTFOLIO.md
> # 看到輸出（文件存在）才能繼續
>
> # 2. wc 確認：
> wc -c docs/TECH/v6.0_PORTFOLIO.md
> # 看到 > 100 bytes 才能聲稱有意義內容
>
> # 3. Read 抽檢：
> head -3 docs/TECH/v6.0_PORTFOLIO.md
> # 看到內容才能確認非空
> ```

**交付清單**（每個任務必須包含）：
- 修改的文件列表
- 測試結果（analyze + test）
- Build 結果
- **AI 自測報告**
- 截圖/演示（如果有 UI 變更）
- PRD 執行記錄更新

**交付質量標準**：
- 測試覆蓋率：關鍵路徑 100%
- 測試通過率：100%
- 分析問題數：0

## Step 7：復盤（四步法）

| 步驟 | 問題 | 輸出 |
|------|------|------|
| 回顧目標 | 用戶要的是什麼？驗收標準是？ | 目標澄清 |
| 評估結果 | 實際交付了什麼？有差距嗎？ | 結果清單 |
| 分析原因 | 彎路的根因是什麼？ | 原因清單 |
| 沉澱規律 | 可復用的經驗是什麼？ | SOP |

---

## 常見問題處理

| 情況 | 動作 |
|------|------|
| 遇到 Bug | 觸發 Debug Flow |
| 需求模糊 | 先澄清再執行，不盲目動手 |
| 發現額外問題 | 主動處理（Owner 意識），不等待用戶提出 |
| 修復後影響範圍不清 | 跑全量測試確認 |
| 測試覆蓋不足 | 先補測試，再寫代碼（TDD 紀律）|
