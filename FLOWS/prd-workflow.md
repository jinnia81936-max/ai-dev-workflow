---

## 核心原則

| 原則 | 說明 |
|------|------|
| **版本單一來源（SSOT）** | 所有功能文檔只存在於 `docs/PRD/` |
| **雙重審批關卡** | PRD 審批通過後才能生成技術方案；技術方案審批通過後才能實現 |
| **版本號遞增** | 每個功能迭代一個新版本 |
| **狀態標注** | 每個功能有 ❌/🔄/⚠️/✅ 明確狀態 |
| **交付有據** | 每次交付有日期+測試者+結果+備註 |

---

## 完整流程（含審批關卡）

```
需求 → PRD 生成 → ⚠️ 我審批 → 技術方案 → ⚠️ 我審批 → 測試用例 → 實現 → AI 自測 → 交付
                ↑                           ↑
           方向不對不動手             方案不對不動手
```

**紀律**：
- PRD 未通過審批 = 不能生成技術方案
- 技術方案未通過審批 = 不能開始實現
- 實現完成後才能交付

## PRD 文件命名規範

```
v{major}.{minor}_{功能簡稱}.md
```

**示例**：
- `v1.0_SPEC.md` — 基礎行情功能
- `v6.0_PORTFOLIO.md` — 投資組合追蹤

| 測試用例審批 | 🔄 待生成 | - | - |

## 版本狀態機

```
❌ 規劃中 → 🔄 起草中 → ⚠️ 待審批 → ✅ 已交付
              ↓              ↓
           ❌ 擱置         🔄 退回修改
```

**狀態定義**：
- ❌ 規劃中：需求已確認，還沒開始寫 PRD
- 🔄 起草中：PRD 正在編寫
- ⚠️ 待審批：PRD 已完成，等待用戶審批
- 🔄 退回修改：審批不通過，需要修改
- ✅ 已交付：實現完成，版本封口

## PRD 維護流程

### 標準流程（每個功能迭代）

```
1. 需求確認 → 產品經理生成 PRD
2. PRD 寫入 docs/PRD/vX.Y_NAME.md（SSOT 驗證：ls + wc）
3. ⚠️ 用戶審批 PRD
   → 不通過：修改後重新提交審批
   → 通過：進入步驟 4
4. 生成技術方案 → 寫入 docs/TECH/vX.Y_NAME.md
5. ⚠️ 用戶審批技術方案
   → 不通過：修改後重新提交審批
   → 通過：進入步驟 6
6. 生成測試用例 → 寫入 docs/TEST/TEST_CASES_vX.md
7. 實現代碼
8. AI 自測驗證（development-flow.md Step 5.5）
9. SSOT 交付前驗證（development-flow.md Step 5.6）
10. 交付 + 更新 PRD 執行記錄
```

### SSOT 強制驗證（每步必做）

```bash
# 文檔寫入後必須立馬驗證
ls -la docs/PRD/vX.Y_NAME.md
wc -c docs/PRD/vX.Y_NAME.md
```

## 版本規劃原則

| 情況 | 版本策略 |
|------|---------|
| 新功能上線 | 新增版本（vX.Y）|
| Bug 修復 | 不新增版本，更新缺陷記錄 |
| 小優化 | 不新增版本，更新對應 PRD |
| 重大重構 | 評估是否需要新版本 |
