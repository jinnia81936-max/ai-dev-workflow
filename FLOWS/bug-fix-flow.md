# Bug 修復閉環流程 v1.1

> 創建日期：2026-04-29
> 更新日期：2026-04-30
> 更新內容：新增 Console 錯誤檢查強制關卡
> 用途：高質量 Bug 修復的標準化流程
> 特性：自動化執行 + SSOT 驗證 + 自測報告

---

## 一、核心原則

| 原則 | 說明 |
|------|------|
| **Owner 意識** | Bug 在你眼前，你就是 Owner。不是"這個 Bug 的"，是"我的 Bug" |
| **根因分析優先** | 不修症狀，修根因。否則同類問題會一直出現 |
| **閉環交付** | Write→ls→wc→Read 機械約束，嚴禁虛假交付 |
| **同類問題掃描** | 修完 A 問題，主動檢查 B/C 同類問題 |

---

## 二、完整流程（含自動化自測）

```
┌─ Bug 修復閉環 ──────────────────────────────────────────────────┐
│                                                                 │
│  1️⃣ 接收 Bug ─────────────────────────────────────────────────►│
│     ↓ 症狀確認 + 複現步驟                                       │
│  2️⃣ 根因分析 ─────────────────────────────────────────────────►│
│     ↓ 5-Why / 揪頭髮 / 7項檢查清單（L3+）                        │
│  3️⃣ 修復方案設計 ─────────────────────────────────────────────►│
│     ↓ 方案評審 + 影響範圍評估                                    │
│  4️⃣ 代碼修復 ─────────────────────────────────────────────────►│
│     ↓ Write tool                                               │
│  5️⃣ SSOT 驗證 ─────────────────────────────────────────────────►│
│     ↓ ls + wc + Read                                           │
│  6️⃣ 自測驗證 ─────────────────────────────────────────────────►│
│     ↓ flutter analyze + test + build                           │
│  7️⃣ 同類問題掃描 ─────────────────────────────────────────────►│
│     ↓ 藍軍自攻擊                                               │
│  8️⃣ 交付報告 ─────────────────────────────────────────────────►│
│     ↓ 自測報告沈澱                                              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 三、步驟詳解

### Step 1：接收 Bug

**輸入**：Bug 描述、復現步驟、截圖/日誌

**動作**：
1. 確認 Bug 等級（P0/P1/P2/P3）
2. 獲取完整復現步驟
3. 識別受影響範圍

**Owner 四問**：
- 這個問題的根因是什麼？
- 還有誰會被影響？（上下游拉通）
- 下次怎麼防止？
- 數據在哪？

---

### Step 2：根因分析

**方法論路由**（根據失敗次數自動切換）：

| 失敗次數 | 等級 | 方法論 |
|---------|------|--------|
| 0-1 次 | L0 | 聞味道 → 揪頭髮 5 步 |
| 2 次 | L1 | ⬛ Musk（質疑需求+刪除）→ 🟣 拼多多（砍中間環節） |
| 3 次 | L2 | ⚫ 百度（搜索第一）→ 🔶 Amazon（Dive Deep） |
| 4 次 | L3 | **7 項檢查清單強制執行** |
| 5+ 次 | L4 | 拼命模式或結構化失敗報告 |

**5-Why 根因分析法**：

```
Bug: TextField controller 未綁定

Why 1: 為什麼搜尋功能失效？
→ 因為 TextField 的 onChanged 收到空字符串

Why 2: 為什麼 onChanged 收到空字符串？
→ 因為 controller 未綁定到 TextField

Why 3: 為什麼 controller 未綁定？
→ 因為使用了匿名 controller 而非成員變量

Why 4: 為什麼使用匿名 controller？
→ 因為代碼簡化了變量聲明

Why 5: 為什麼簡化變量聲明？
→ 因為沒有理解 TextField controller 生命周期

根因: TextField controller 需要在 StatefulWidget 生命周期內管理
```

**7 項檢查清單（L3+ 強制）**：
- [ ] 逐字读完失败信号了吗？
- [ ] 用工具搜索过核心问题了吗？
- [ ] 读过失败位置的原始上下文了吗？
- [ ] 所有假设都用工具确认了吗？
- [ ] 试过完全相反的假设吗？
- [ ] 能在最小范围内复现问题吗？
- [ ] 换过工具/方法/角度/技术栈吗？

---

### Step 3：修復方案設計

**方案評審清單**：
- [ ] 修復是否引入新問題？
- [ ] 影響範圍是否可控？
- [ ] 是否符合現有架構？
- [ ] 是否有更好的解決方案？

**影響範圍評估**：
```bash
# 搜索相關代碼
grep -r "受影響關鍵詞" lib/

# 檢查依賴關係
flutter analyze
```

---

### Step 4：代碼修復

**機械約束**：
1. Write tool → 文件寫入磁盤
2. **立即執行** ls + wc + Read（不等用戶催）

**代碼規範**：
- 不破壞現有功能
- 添加必要的註釋
- 符合項目代碼風格

---

### Step 5：SSOT 驗證

**強制執行**：
```bash
# 1. Write tool 後立即執行
ls -la {修復文件路徑}
wc -c {修復文件路徑}
head -3 {修復文件路徑}

# 2. 確認文件存在且非空
# 看到輸出才能繼續
```

**防虛假交付模式**：
```
❌ 只說"已修復"
❌ 只說"已寫入"
❌ 回覆用戶前未執行 ls/wc/Read
```

---

### Step 6：自測驗證

**標準化自測命令序列**：

```bash
# 1. 代碼分析
flutter analyze

# 2. 單元測試 + Widget 測試
flutter test

# 3. iOS Build 驗證
flutter build ios --simulator --no-codesign

# 4. Device Console 錯誤檢查 ← 必須執行
xcrun simctl spawn "iPhone 16 Pro" log show --predicate 'subsystem == "Flutter"' --last 1m 2>&1 | grep -i error

# 5. 回歸測試（不破壞現有功能）
# 確保現有測試仍然通過
```

**測試用例對照（Bug 修復專項）**：

> Bug 修復也必須對照測試用例逐項驗證，確保修復完整

| 驗證方法 | 能發現 | 不能發現 |
|---------|---------|---------|
| 截圖 | UI 佈局 | Runtime 錯誤 |
| flutter analyze | 靜態分析錯誤 | 運行時崩潰 |
| **Console 檢查** | **Runtime 錯誤** | - |

**合格標準**：`error` 出現次數 = 0

**Bug 修復專項測試**：

| 測試類型 | 覆蓋場景 |
|---------|---------|
| 單元測試 | 模型方法邏輯 |
| Widget 測試 | UI 組件交互 |
| 集成測試 | 完整流程 |
| 邊界測試 | 異常輸入、空值、零值 |

### Step 7：同類問題掃描（藍軍自攻擊）

**自動化同類問題檢測**：

```bash
# 1. 搜索同類關鍵詞
grep -r "出問題的代碼模式" lib/

# 2. 檢查相似模塊
# 例如：修復了 SearchPage 的 TextField，檢查其他 Page 的 TextField

# 3. 上下遊影響評估
# 改了 A 組件，B/C 是否受影響？
```

**藍軍自攻擊清單**：
- [ ] 同模塊是否有類似問題？
- [ ] 相鄰模塊是否受影響？
- [ ] 邊界條件是否處理？
- [ ] 異常輸入是否會崩潰？

## 四、Bug 等級定義

| 等級 | 定義 | 響應時間 | 自測要求 |
|------|------|---------|---------|
| P0 | 核心功能崩潰、數據丟失 | 立即 | 完整自測 + 回歸測試 |
| P1 | 重要功能失效 | 4h | 完整自測 |
| P2 | 次要功能異常 | 24h | 標準自測 |
| P3 | 界面/體驗問題 | 72h | 基礎自測 |

## 五、自動化觸發條件

**自動執行場景**：
1. 用戶報告 Bug → 自動進入 Bug 修復流程
2. 測試失敗 → 自動進入根因分析
3. Build 失敗 → 自動進入 Debug 流程
4. 連續 2 次同類問題 → 升級 L1，自動切換方法論

**自動通知**：
- 修復完成 → 自動生成自測報告
- 發現同類問題 → 自動標記並通知
- 無法解決 → 自動生成結構化失敗報告

## 六、防虛假交付機制

**機械約束（強制執行）**：
```
1. Write tool → 文件寫入磁盤
2. Bash ls → 確認文件存在（立馬執行，不等用戶催）
3. Bash wc -c → 確認文件大小 > 100 bytes
4. Read tool → 抽檢前 3 行確認非空
5. 才能回覆用戶"已交付"
```

**紅線警示**：
| 紅線 | 違背動作 |
|------|---------|
| 紅線一 | 聲稱完成但沒有輸出證據 |
| 紅線二 | 未驗證文件存在就聲稱交付 |
| 紅線三 | 跳過了 Write tool 的簡單驗證 |
