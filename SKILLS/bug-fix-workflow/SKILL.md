# Bug 修復閉環工作流技能

## 摘要

嚴格遵守「問題 → bug分析報告 → ⚠️ 用戶審批 → bug修復技術方案 → ⚠️ 用戶審批 → 測試用例 → ⚠️ 用戶審批 → 實現 → AI 自測 → 交付」的閉環修復流程。每個階段必須獲得用戶審批後才能進入下一階段。

---

## 何時使用

| 情況 | 行動 |
|------|------|
| 收到 Bug 報告 | 從階段一：Bug 分析報告開始 |
| Bug 分析報告已審批通過 | 進入階段二：Bug 修復技術方案 |
| Bug 修復技術方案已審批通過 | 進入階段三：測試用例 |
| 測試用例已審批通過 | 進入階段四：實現 |
| 實現完成 | 執行階段五：AI 自測 → 階段六：交付 |

---

## 紅線規則（不可違反）

### 規則一：審批門禁
每個階段必須獲得用戶 ✅ 審批通過後才能進入下一階段，絕對不允許跳過。

### 規則二：根因分析優先
未完成根因分析不得設計修復方案。禁止「先試試看」式的盲目修復。

### 規則三：SSOT 交付驗證
每次聲稱「已修復」前，必須依序執行 Write → ls → wc -c → Read，用機械約束防止假交付。

### 規則四：同類問題掃描（藍軍自攻擊）
修復完成後必須掃描同一模塊、上下游相關模塊是否存在同類問題。

## 階段一：問題 → Bug 分析報告

**負責方**：AI Agent

**步驟**：

1. **理解問題**
   - 確認 Bug 症狀和複現步驟
   - 從用戶收集完整信息（環境、版本、操作步驟）

2. **根因分析（5-Why）**
   - Why 1：表面現象的原因是什麼？
   - Why 2：第一層原因的背後原因是什麼？
   - Why 3：第二層原因的背後原因是什麼？
   - Why 4：第三層原因的背後原因是什麼？
   - Why 5：找到根本原因

3. **影響範圍評估**
   - 哪些功能受影響？
   - 哪些用戶場景受影響？
   - 是否有數據損壞風險？

4. **生成 Bug 分析報告**
   - 路徑：`docs/BUG/v{major}.{minor}_BUG_{NAME}.md`
   - 必須包含：
     - Bug 基本信息（編號、版本、嚴重等級 P0-P3）
     - 複現步驟
     - 根因分析（5-Why 鏈）
     - 影響範圍評估
     - 相關代碼位置

5. **SSOT 驗證**
   ```bash
   ls -la docs/BUG/v{major}.{minor}_BUG_{NAME}.md
   wc -c docs/BUG/v{major}.{minor}_BUG_{NAME}.md
   head -10 docs/BUG/v{major}.{minor}_BUG_{NAME}.md
   ```

6. **提交審批**

**審批請求格式：**
```
⚠️ [審批請求] Bug 分析報告已生成，等待您的審批

文件：docs/BUG/v{major}.{minor}_BUG_{NAME}.md
Bug 編號：BUG-XXX
嚴重等級：P0/P1/P2/P3
根因：{一句話描述根因}

請確認：
- 根因分析是否準確？
- 影響範圍評估是否完整？
- 複現步驟是否清晰？

回覆「批准」繼續，或「需修改」+ 具體要求
```

## ⚠️ 用戶審批（門禁 1）

用戶審核 Bug 分析報告。

| 結果 | 行動 |
|------|------|
| ✅ 批准 | 進入階段二：Bug 修復技術方案 |
| ❌ 需修改 | 根據反饋修改後重新提交審批 |

---

## 階段二：Bug 修復技術方案

**負責方**：AI Agent  
**前置條件**：Bug 分析報告審批通過

**步驟**：

1. **分析 Bug 分析報告**
   - 閱讀已審批的報告
   - 確認根因和影響範圍

2. **設計修復方案**
   - 路徑：`docs/TECH/v{major}.{minor}_BUGFIX_{NAME}.md`
   - 必須包含：
     - 修復目標（關聯 Bug 編號）
     - 現有問題代碼分析
     - 修復方案設計（每個文件的修改內容）
     - 數據修復策略（如有數據損壞）
     - 回歸風險評估
     - 執行計劃

3. **SSOT 驗證**
   ```bash
   ls -la docs/TECH/v{major}.{minor}_BUGFIX_{NAME}.md
   wc -c docs/TECH/v{major}.{minor}_BUGFIX_{NAME}.md
   head -10 docs/TECH/v{major}.{minor}_BUGFIX_{NAME}.md
   ```

4. **提交審批**

**審批請求格式：**
```
⚠️ [審批請求] Bug 修復技術方案已生成，等待您的審批

文件：docs/TECH/v{major}.{minor}_BUGFIX_{NAME}.md
Bug 編號：BUG-XXX
修改文件：共 N 個

請確認：
- 修復方案是否解決了根因（而非症狀）？
- 修改範圍是否最小化？
- 回歸風險是否可控？

回覆「批准」繼續，或「需修改」+ 具體要求
```

## 階段三：測試用例

**負責方**：AI Agent  
**前置條件**：Bug 修復技術方案審批通過

**步驟**：

1. **分析修復方案**
   - 閱讀已審批的修復方案
   - 理解修改範圍

2. **生成測試用例**
   - 文檔路徑：`docs/TEST/TEST_CASES_BUGFIX_v{major}.{minor}_{NAME}.md`
   - 代碼路徑：`test/{feature}_test.dart`（追加或新建）

   **測試用例結構：**

   | TC-XXX | 模塊 | 測試項 | 優先級 | 前置條件 | 測試步驟 | 預期結果 | 斷言 |
   |--------|------|--------|--------|---------|---------|---------|------|

   **必須覆蓋的測試類型：**
   - Bug 複現測試（確認 Bug 可被複現）
   - 單元測試（修復邏輯的正確性）
   - Widget 測試（UI 交互修復）
   - 回歸測試（確保不破壞現有功能）
   - 邊界測試（極端輸入、空值、邊界條件）

3. **SSOT 驗證**
   ```bash
   ls -la docs/TEST/TEST_CASES_BUGFIX_v{major}.{minor}_{NAME}.md
   wc -c docs/TEST/TEST_CASES_BUGFIX_v{major}.{minor}_{NAME}.md
   ```

4. **提交審批**

**審批請求格式：**
```
⚠️ [審批請求] Bug 修復測試用例已生成，等待您的審批

文檔：docs/TEST/TEST_CASES_BUGFIX_v{major}.{minor}_{NAME}.md
Bug 編號：BUG-XXX
測試項：共 N 項（複現: X, 單元: Y, Widget: Z, 回歸: W）

請確認：
- Bug 複現測試是否覆蓋了原始場景？
- 邊界條件是否覆蓋？
- 回歸測試是否足夠？

回覆「批准」繼續，或「需修改」+ 具體要求
```

## 階段四：實現

**負責方**：AI Agent  
**前置條件**：測試用例審批通過

**步驟**：

1. 依照修復方案修改代碼
2. 同步編寫或更新測試代碼
3. 確保現有測試不受影響（回歸安全）
4. 每個文件完成後執行 SSOT 驗證（ls + wc）

---

## 階段五：AI 自測

**負責方**：AI Agent  
**前置條件**：實現完成

### 5.1 標準化自測命令（全部強制執行，必須展示輸出）

```bash
# 步驟 1：靜態代碼分析
flutter analyze
# 合格標準：0 issues

# 步驟 2：運行測試
flutter test
# 合格標準：All tests passed

# 步驟 3：構建驗證
flutter build ios --simulator --no-codesign
# 合格標準：構建成功

# 步驟 4：Console 錯誤檢查
xcrun simctl spawn "iPhone 16 Pro" log show --predicate 'subsystem == "Flutter"' --last 1m 2>&1 | grep -i error
# 合格標準：0 errors（排除與本次修復無關的已有錯誤）

# 步驟 5：Bug 複現驗證
# 按原始複現步驟操作，確認 Bug 不再出現

# 步驟 6：同類問題掃描（藍軍自攻擊）⚠️ 必做
# 搜索同一模塊、上下游相關模塊是否存在同類問題
grep -r "{問題關鍵詞}" lib/
```

### 5.2 測試用例執行報告

```
| TC | 測試項 | 狀態 |
|----|--------|------|
| TC-001 | Bug 複現測試 | ✅ |
| TC-002 | 修復邏輯測試 | ✅ |
| TC-003 | 回歸測試 | ✅ |
```

## 階段六：交付

**負責方**：AI Agent → 用戶  
**前置條件**：所有自測通過

### 6.1 SSOT 交付驗證

```bash
# 確認所有修改文件存在且非空
ls -la <每個修改文件路徑>
wc -c <每個修改文件路徑>
head -3 <每個修改文件路徑>
```

### 6.2 交付格式

```
✅ Bug 修復交付驗收

Bug 編號：BUG-XXX
嚴重等級：P0/P1/P2/P3

修改文件：
- lib/... (N 個文件)
- test/... (N 個文件)

自測結果：
- flutter analyze: 0 issues ✅
- flutter test: X/Y passed ✅
- flutter build: 成功 ✅
- Console check: 0 errors ✅
- Bug 複現驗證：已修復，不再出現 ✅
- 同類問題掃描：無同類問題 ✅

測試用例覆蓋：
- 全部 TC 通過 ✅

請確認驗收
```

## Bug 嚴重等級定義

| 等級 | 含義 | 響應時限 |
|------|------|---------|
| P0 | 核心崩潰 / 數據丟失 / 安全漏洞 | 立即修復 |
| P1 | 核心功能無法使用 | 4 小時內 |
| P2 | 非核心功能異常 | 24 小時內 |
| P3 | UI/UX 小問題 | 72 小時內 |

## 文檔目錄擴展

```
項目根目錄/
├── docs/
│   ├── PRD/       ← 產品需求文檔（新功能開發）
│   ├── TECH/      ← 技術方案文檔（新功能開發 + Bug 修復）
│   ├── TEST/      ← 測試用例文檔（新功能開發 + Bug 修復）
│   └── BUG/       ← Bug 分析報告
└── test/          ← 代碼測試文件
```

| 類型 | 路徑 | 命名規則 |
|------|------|---------|
| Bug 分析報告 | `docs/BUG/` | `v{major}.{minor}_BUG_{NAME}.md` |
| Bug 修復方案 | `docs/TECH/` | `v{major}.{minor}_BUGFIX_{NAME}.md` |
| Bug 測試用例 | `docs/TEST/` | `TEST_CASES_BUGFIX_v{major}.{minor}_{NAME}.md` |

## 審批狀態定義

| 狀態 | 標記 | 含義 |
|------|------|------|
| 起草中 | 🔄 | 文檔正在編寫 |
| 待審批 | ⚠️ | 完成，等待用戶審批 |
| 已通過 | ✅ | 用戶審批通過，可進入下一階段 |
| 已拒絕 | ❌ | 需修改後重新提交 |

---

## 同類問題掃描（藍軍自攻擊）清單

修復完成後必須檢查：

1. **同一模塊**：相同組件/函數是否有相同模式錯誤？
2. **上游模塊**：調用方是否有相同處理不當？
3. **下游模塊**：被調用方是否有相同參數問題？
4. **邊界情況**：空值、極限值、網絡異常是否處理？
5. **異常輸入**：特殊字符、超長輸入是否會導致問題？
